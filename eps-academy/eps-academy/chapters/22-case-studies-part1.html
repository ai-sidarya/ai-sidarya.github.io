Chapter 22: Integrated Case Studies

Source statusDrafted with AI. Verify standards and product details against primary sources before relying on them.
TakeawayStrong leaders diagnose facts, frame unknowns, choose options deliberately, act fast in the first 24 hours, communicate clearly, and prevent recurrence.

1. Case Study A — Unintended Assist Incident Before a Milestone Core

Facts

During pre‑milestone vehicle tests, a driver reports unintended assist during a tight maneuver. Logs show a transient torque spike. No DTCs. Calibration unchanged. Software build is new. OEM milestone review is in 48 hours.

Unknowns

  • Is the spike reproducible?
  • Is it software timing, sensor noise, or calibration interpolation?
  • Is the issue limited to one vehicle or systemic?
  • Does the safety case already cover this maneuver?
  • Is containment needed before milestone?

Options

  • Option A: Delay milestone, investigate fully.
  • Option B: Apply containment (assist limit) and proceed with milestone.
  • Option C: Proceed with milestone, commit to rapid follow‑up.

Recommended Decision

Choose Option B: apply containment, proceed with milestone with transparent communication. Safety risk is low but non‑zero; containment reduces exposure.

First 24 Hours

  • Reproduce issue on test bench and vehicle.
  • Run targeted SIL/HIL tests around maneuver extremes.
  • Apply temporary assist‑limit containment.
  • Prepare clear milestone briefing: facts, containment, next steps.

Communication

To OEM: “We observed a transient assist spike in a specific maneuver. Containment is applied. Investigation is underway. No safety concerns at this time. We will provide updates every 48 hours.”

Prevention

  • Add combined maneuver tests to regression suite.
  • Expand calibration interpolation checks.
  • Improve sensor noise filtering validation.

Tough Follow‑Up

Ask calibration and software leads: “Why did our tests not cover this maneuver? What escape point allowed this through?”

2. Case Study B — ASIL D Evidence Incomplete at Release Core

Facts

Release date is in two weeks. Safety case shows missing evidence for two ASIL D safety goals. HIL tests incomplete. OEM expects full ASIL D package. Program pressure is high.

Unknowns

  • Is missing evidence due to test gaps or analysis gaps?
  • Can tests be completed in time?
  • Are safety goals incorrectly scoped?
  • Does OEM accept staged evidence?

Options

  • Option A: Delay release until evidence is complete.
  • Option B: Deliver staged evidence with clear risk statement.
  • Option C: Re‑scope safety goals (dangerous if unjustified).

Recommended Decision

Choose Option B: staged evidence with explicit risk and timeline. Never re‑scope safety goals without strong justification.

First 24 Hours

  • Identify exact missing evidence.
  • Run accelerated HIL tests with clear coverage boundaries.
  • Prepare staged safety case addendum.
  • Align with safety lead and OEM safety counterpart.

Communication

To OEM: “Two ASIL D goals have incomplete evidence. We propose staged delivery: partial evidence now, full evidence in 3 weeks. No known safety risk. Here is the detailed plan.”

Prevention

  • Introduce safety case progress dashboards.
  • Link safety goals to test coverage explicitly.
  • Run mid‑cycle safety case audits.

Tough Follow‑Up

Ask safety team: “Why did we discover missing evidence this late? What structural change prevents recurrence?”

3. Case Study C — Two Regions Blaming Each Other Core

Facts

Region A owns torque‑control software. Region B owns calibration. Steering oscillations appear in integration. Region A claims calibration changed without notice. Region B claims software timing changed. Diagnostics unclear.

Unknowns

  • Which change triggered oscillations?
  • Are interface specs outdated?
  • Is timing or calibration the root cause?
  • Are diagnostics misleading?

Options

  • Option A: Escalate to executives (premature).
  • Option B: Run cross‑region blameless review.
  • Option C: Freeze both changes and roll back.

Recommended Decision

Choose Option B: structured cross‑region blameless review with interface owner leading.

First 24 Hours

  • Assign interface owner for control–calibration boundary.
  • Collect logs, traces, timing diagrams.
  • Run joint SIL/HIL tests with both regions present.
  • Document findings in shared workspace.

Communication

To both regions: “We will run a blameless integration review. Focus on system behavior, not fault. Interface owner leads. Goal: identify root cause within 48 hours.”

Prevention

  • Introduce cross‑region integration rituals.
  • Update interface agreements and decision rights.
  • Improve diagnostics clarity.

Tough Follow‑Up

Ask both regions: “What structural gaps allowed this conflict? How do we prevent cross‑region blame cycles?”

4. Case Study D — Third‑Party Dependency Vulnerability Core

Facts

A third‑party library used in EPS diagnostics has a newly disclosed vulnerability. Exploit allows unauthorized access to logs. Library is used in both development and vehicle tooling. OEM asks for impact assessment within 24 hours.

Unknowns

  • Is EPS ECU exposed or only tooling?
  • Is vulnerability exploitable in vehicle context?
  • Is patch available?
  • Does patch affect timing or memory?

Options

  • Option A: Patch immediately without analysis (risky).
  • Option B: Assess exposure, apply containment, plan patch.
  • Option C: Remove dependency entirely (slow).

Recommended Decision

Choose Option B: assess exposure, apply containment, plan patch with full validation.

First 24 Hours

  • Identify where library is used.
  • Assess exploitability in EPS context.
  • Disable vulnerable diagnostic paths temporarily.
  • Prepare OEM briefing: exposure, containment, patch plan.

Communication

To OEM: “Vulnerability affects diagnostic tooling, not EPS ECU. Containment applied. Patch planned within 72 hours. No vehicle safety impact.”

Prevention

  • Introduce SBOM tracking.
  • Run periodic dependency audits.
  • Define patch validation flow for safety‑critical systems.

Tough Follow‑Up

Ask security team: “Why was dependency risk not flagged earlier? How do we strengthen SBOM governance?”
