Chapter 04: Reading Embedded C and Scripts

Source statusDrafted with AI. Verify standards and product details against primary sources before relying on them.
TakeawayIf you cannot read embedded C precisely, you cannot judge EPS software safety, timing, or failure modes.

1. What you must know Core

Reading embedded C is about spotting risks, not writing code. You must understand how volatile, const, static, pointers, and bit operations affect timing and correctness. You must recognize undefined behavior, integer overflow, and signed versus unsigned traps.

Interrupt Service Routines (ISRs) require special care. ISR-safe code avoids blocking, shared-state races, and long execution. MISRA concepts guide safer C usage by restricting dangerous constructs. Static analysis tools detect defects early but require interpretation.

Scripts matter too. Build scripts, flashing scripts, and test scripts become production infrastructure when they control releases or diagnostics. You must read them with the same rigor as C code.

2. How it works Working

Embedded C interacts directly with hardware. volatile tells the compiler a variable can change outside normal code flow. const marks data that must not change. static controls lifetime and visibility.

Pointers access memory directly. Bit operations pack or unpack sensor data. Integer overflow occurs when arithmetic exceeds type limits. Signed versus unsigned mismatches cause subtle bugs.

Undefined behavior is any operation where the C standard gives no guarantee. Examples include out-of-bounds access or shifting by too many bits. Undefined behavior can break timing and torque control.

Read variable→Check qualifiers→Check type→Check concurrency→Check side effects

Static analysis tools scan code for defects. They flag risky patterns, but not all warnings matter. You must judge which warnings affect safety goals. Unit-test seams are places where code can be isolated for testing.

3. EPS example Working

EPS torque control reads torque and angle sensors, computes assist, and updates PWM. C code handles ADC results, scaling, filtering, and plausibility checks. Communication code handles CAN or Ethernet frames.

volatile is required for ADC result registers. const is required for calibration tables. static may hold filter history. Bit operations pack torque values into CAN frames.

Signed versus unsigned errors can flip torque direction. Integer overflow can saturate torque commands. Undefined behavior can corrupt sensor data. ISR-safe code ensures torque updates remain deterministic.

4. How it fails (concrete scenario) Interview depth

Consider a torque sensor read implemented without volatile. The compiler optimizes away repeated reads. The code uses a cached value instead of the latest sensor reading.

During fast steering maneuvers, the cached value lags behind reality. Torque control computes assist from stale data. The driver feels a brief steering pull.

Another failure involves signed versus unsigned mismatch. A negative torque offset is stored in an unsigned variable. The value wraps to a large positive number. The system commands unintended assist.

Undefined behavior also causes failures. A bit shift by more than the width of the type yields unpredictable results. Torque scaling becomes erratic. Steering feel degrades.

Scripts fail too. A flashing script silently skips a calibration file. The ECU runs with default torque limits. The vehicle feels heavy at low speed. The issue appears only in certain builds.

5. What a manager decides Interview depth

You decide how deeply the team reviews C code. You choose whether volatile, const, and static usage is audited. You decide whether signed versus unsigned mismatches are banned.

Customer implications are direct. OEMs expect predictable torque behavior. If you cannot explain a defect caused by undefined behavior, trust erodes. You must ensure code is readable and defensible.

Safety implications are severe. ASIL D torque-control goals require deterministic behavior. Undefined behavior breaks determinism. Integer overflow breaks plausibility. ISR races break timing.

Cybersecurity interacts with scripts. Build scripts that handle keys or flashing become attack surfaces. If scripts become production infrastructure, they must be reviewed like code.

Schedule implications matter. Deep code reviews take time. Static analysis warnings require triage. You decide whether to delay features to fix foundational defects.

6. Questions a strong manager asks the team Interview depth

Strong questions expose unsafe assumptions. They focus on reading, not writing.

  • “Show me where volatile is required for hardware registers.”
  • “Which calibration values must be const, and how do we enforce it?”
  • “Where do we mix signed and unsigned types in torque calculations?”
  • “Which operations rely on undefined behavior or compiler quirks?”
  • “How do we ensure ISR-safe access to shared variables?”
  • “Which static analysis warnings affect torque control?”
  • “Which scripts are now production infrastructure, and who owns them?”

7. Weak answer versus strong answer Interview depth

Weak

Strong

“We review volatile usage for all hardware registers and ISR-shared variables. We enforce const for calibration. We scan for signed/unsigned mismatches and undefined behavior. Static analysis warnings are triaged by safety impact. Scripts that control flashing or builds are treated as production infrastructure.”

The weak answer trusts tools and rules blindly. It ignores reading and reasoning. It misses safety implications.

The strong answer shows active judgment. It connects C constructs to torque behavior. It treats scripts as part of the product.

8. What the interviewer is testing Working

Interviewers test whether you can read embedded C at leadership depth. They want to see if you can spot risks without writing code. They check whether you understand how C constructs affect EPS torque control.

They also test your ability to reason about scripts. They want to know if you treat build and flashing scripts as production infrastructure. They check whether you understand debugging flow.

They test your ability to connect defects to safety goals. They want to see if you can explain how undefined behavior breaks determinism.

9. Common mistakes (beginner and executive) Working

Beginners assume volatile is optional. They trust the compiler to read hardware registers correctly. They ignore signed versus unsigned traps.

Beginners also misunderstand static. They think static means “fast,” not “persistent.” They miss hidden state that breaks tests.

Executives assume MISRA compliance guarantees safety. They treat static analysis warnings as noise. They ignore scripts until they break releases.

Executives may also skip reading code. They rely on summaries. They miss subtle defects that cause torque spikes.

11. Exercise with answer notes Expert

Five short code snippets with defects:

Snippet 1 
uint16_t torque;
uint16_t *p = &torque;
*p = *p + 50000;  // defect

Defect: Integer overflow wraps silently. Torque spikes possible.

Answer notes: Check type limits. Use saturation logic. Review scaling.

Snippet 2 
uint16_t adc_val = ADC_REG;  // missing volatile

Defect: ADC_REG must be volatile. Compiler may cache value.

Answer notes: Hardware registers require volatile. Review ISR paths.

Snippet 3 
static int offset = -10;
uint16_t torque = offset + sensor;  // signed/unsigned mix

Defect: Negative offset becomes large positive when cast.

Answer notes: Align types. Validate ranges. Check plausibility.

Snippet 4 
uint8_t scale = 8;
uint16_t val = raw << scale;  // undefined if raw too large

Defect: Shift may exceed type width. Undefined behavior.

Answer notes: Check bounds. Use safe shift macros.

Snippet 5 
ISR(void)
{
    shared++;  // not atomic
}

Defect: Race condition with main code. ISR-safe access missing.

Answer notes: Use atomic operations or disable interrupts briefly.

Debugging method:

  • Reproduce: Capture exact steering maneuver, speed, and environment.
  • Capture configuration: Record build version, calibration, and scripts used.
  • Isolate: Reduce variables. Disable features. Log internal states.
  • Root cause versus escape point: Root cause is the defect. Escape point is where the system failed to detect it.

When scripts become production infrastructure: Scripts become production infrastructure when they control builds, flashing, diagnostics, or release packaging. They must be versioned, reviewed, and tested like code.
