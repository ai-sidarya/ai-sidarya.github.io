Chapter 11: GitHub and GitHub Actions

Source statusDrafted with AI. Verify standards and product details against primary sources before relying on them.
TakeawayIf you cannot read GitHub workflows, you cannot judge EPS software evidence, security, or release control.

1. What you must know Core

GitHub is a source-hosting platform. GitHub Actions is its automation engine. Together they control builds, tests, and releases.

Protected branches enforce rules before changes land. CODEOWNERS define who must review changes. Required checks ensure workflows pass before merging. These controls shape what reaches EPS torque-control code.

Workflows are automation definitions. Jobs are units of work inside workflows. Runners execute jobs. Hosted runners are provided by GitHub. Self-hosted runners run on your own machines.

Secrets store sensitive values such as tokens or keys. Permissions define what workflows can do. OIDC (OpenID Connect) allows short-lived cloud credentials without long-lived secrets. Reusable workflows share logic across repositories.

Third-party actions are prebuilt steps from others. Pinning means locking them to specific versions or commits. Fork risks arise when external contributors run workflows. Artifact attestations describe how build outputs were produced.

2. How it works Working

GitHub Actions uses YAML files to define workflows. Each workflow has triggers, jobs, and steps. Triggers include push, pull_request, and schedule.

Jobs run on runners. Each job has a name, runs-on setting, and steps. Steps call actions or run shell commands. Actions can be official, internal, or third-party.

Protected branches require status checks and reviews. CODEOWNERS files map paths to reviewers. Required checks link workflows to branch protection. Together they enforce process before code merges.

Developer pushes change→Workflow runs on runner→Checks report status→Protected branch enforces rules→Merge or block

Secrets are stored in GitHub and injected into workflows. Permissions control which APIs workflows can call. OIDC lets workflows request cloud tokens dynamically. Reusable workflows centralize patterns such as build-and-test or release packaging.

3. EPS example Working

Imagine an EPS repository hosting torque-control software. The main branch represents integration. A release branch represents candidate software for vehicles.

Protected branches block direct pushes. Only pull requests can change main or release. CODEOWNERS require reviews from safety, architecture, and calibration leads for specific directories.

Required checks include unit tests, integration tests, static analysis, and HIL trigger workflows. Self-hosted runners build binaries using the same toolchain as production. Hosted runners handle lighter tasks such as documentation.

Secrets store tokens for artifact storage, issue trackers, and cloud HIL orchestration. Permissions restrict workflows to necessary scopes. OIDC is used to obtain short-lived tokens for cloud storage or signing services.

Reusable workflows implement common patterns: build-and-test, static-analysis, release-packaging. Third-party actions handle tasks such as caching, notifications, or SBOM generation. Pinning locks them to known versions.

Artifact attestations record build metadata: commit, workflow, runner type, toolchain version, and environment. Release decisions reference these attestations as part of the evidence chain.

4. How it fails (concrete scenario) Interview depth

Consider a repository where protected branches are misconfigured. Required checks cover unit tests only. Integration and safety tests run in optional workflows.

A change to torque-control timing passes unit tests but breaks integration. The pipeline is green. The pull request merges. Vehicles receive software with subtle steering jerks under combined maneuvers.

Another failure involves secrets and permissions. A workflow runs on a self-hosted runner with broad permissions. Secrets include long-lived tokens for artifact storage. A compromised runner leaks tokens. Attackers can upload or replace binaries.

Third-party actions can fail too. A workflow uses an unpinned action from a public repository. The action changes behavior or is compromised. Builds start including unexpected steps. Evidence becomes unreliable.

Fork risks appear when external contributors open pull requests. Workflows may run with access to secrets or internal resources. If branch protection and workflow permissions are weak, attackers can exfiltrate data or manipulate artifacts.

Artifact attestations can be missing or ignored. Release decisions rely on binary hashes only. When a defect appears, nobody can reconstruct which workflow or runner produced the binary. Root-cause analysis stalls.

5. What a manager decides (customer, safety, cybersecurity, schedule implications) Interview depth

You decide which branches are protected and how strictly. You choose which checks are required. You decide who appears in CODEOWNERS for safety-critical paths.

Customer implications are direct. OEMs ask how you control changes to steering software. They expect clear rules for reviews and tests. Weak branch protection undermines trust.

Safety implications involve evidence. ASIL D torque-control goals rely on credible test results and build provenance. If workflows can bypass tests or produce untraceable binaries, the safety case weakens.

Cybersecurity implications involve secrets, runners, and third-party actions. You decide whether self-hosted runners are hardened. You decide whether OIDC replaces long-lived tokens. You decide whether third-party actions are pinned and reviewed.

Schedule implications include pipeline design and maintenance. Strong controls may slow merges. Weak controls may speed merges but increase risk. You must balance throughput with safety and security.

A green pipeline is evidence, not release approval. It shows that defined checks passed. It does not prove that checks are sufficient or that workflows are secure. Release decisions must consider pipeline design, artifact attestations, and safety case status.

6. Questions a strong manager asks the team Interview depth

Strong questions connect GitHub mechanics to steering risk and evidence quality.

  • Branch control: “Which branches gate EPS releases, and what protections apply?”
  • Reviews: “How does CODEOWNERS ensure safety, architecture, and calibration review for torque-control changes?”
  • Checks: “Which workflows are required before merging, and what do they test?”
  • Runners: “Which jobs run on self-hosted runners, and how are those runners secured?”
  • Secrets and permissions: “Which secrets exist, who can use them, and what are workflow permissions?”
  • Third-party actions: “Which external actions do we use, and how are they pinned and reviewed?”
  • Forks: “How do we handle workflows for pull requests from forks without exposing secrets?”
  • Attestations: “How do artifact attestations feed into release decisions and incident analysis?”

7. Weak answer versus strong answer Interview depth

Weak

“We use GitHub Actions and protected branches. All tests run automatically, and the pipeline is green. Self-hosted runners are internal, so they’re safe. Third-party actions are popular and well maintained.”

Strong

“Main and release branches are protected with required checks for unit, integration, static analysis, and safety-related tests. CODEOWNERS enforce review from safety, architecture, and calibration leads for torque-control paths. Self-hosted runners are hardened, isolated, and used only for safety-critical builds, with minimal permissions. Third-party actions are pinned to specific commits and reviewed. Fork pull requests run limited workflows without secrets. Artifact attestations record build provenance and are referenced in release and incident reviews.”

The weak answer hides behind generic claims. It ignores specific controls, risks, and evidence. It treats “internal” as synonymous with “secure.”

The strong answer names concrete protections and practices. It connects GitHub configuration to safety, security, and release decisions. It shows active management of risks.

8. What the interviewer is testing Working

Interviewers test whether you can read GitHub configuration at leadership depth. They want to see if you understand protected branches, CODEOWNERS, required checks, and workflows as control mechanisms.

They also test your security awareness. Do you talk about secrets, permissions, runners, and third-party actions? Do you recognize fork risks and artifact provenance? Do you connect pipeline design to safety and cybersecurity?

They test your ability to ask sharp questions and make decisions. Do you challenge vague “green pipeline” claims? Do you insist on pinned actions and hardened runners? Do you treat GitHub configuration as part of the EPS product environment?

9. Common mistakes (beginner and executive) Working

Beginners treat workflows as magic. They copy YAML from examples without understanding triggers, permissions, or runner choices. They assume more automation always means more safety.

Beginners also ignore secrets and third-party actions. They store long-lived tokens as secrets and use unpinned actions. They do not consider how forks or compromised runners could abuse workflows.

Executives may treat GitHub as “just tooling.” They focus on features and safety cases. They assume DevOps teams handle pipelines. They do not ask how branch protection and required checks relate to release readiness.

Executives may also overtrust green dashboards. They see passing checks as proof of quality. They do not ask which tests run, what coverage exists, or how artifacts are traced. They ignore artifact attestations and provenance.

Another mistake is mixing safety-critical and non-critical workflows without distinction. Leaders allow experimental workflows to run on the same runners with broad permissions. Boundaries blur. Risks increase.

Illustrative YAML Example 1: Basic protected-branch workflow (illustrative)

Illustrative 
name: eps-ci

on:
  pull_request:
    branches: [ main, release ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build
        run: ./build.sh
      - name: Test
        run: ./run-tests.sh

Line-by-line explanation:

  • name: Labels the workflow as “eps-ci” for dashboards.
  • on: Defines trigger. Here, pull requests targeting main or release branches.
  • branches: Limits trigger to protected branches main and release.
  • jobs: Starts job definitions. Each job runs independently.
  • build-and-test: Names the job that builds and tests EPS code.
  • runs-on: Uses a hosted Ubuntu runner. Suitable for non-safety-critical builds.
  • steps: Lists actions and commands executed in order.
  • actions/checkout@v4: Checks out repository code at a pinned version of the checkout action.
  • Build step: Runs build script. Must be deterministic and logged.
  • Test step: Runs test script. Required check status depends on this step.

Illustrative YAML Example 2: Self-hosted runner with limited permissions (illustrative)

Illustrative 
name: eps-release-build

on:
  push:
    branches: [ release ]

permissions:
  contents: read
  packages: write

jobs:
  build-release:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
      - name: Build release binary
        run: ./build-release.sh
      - name: Upload artifact
        run: ./upload-artifact.sh

Line-by-line explanation:

  • name: Labels workflow for release builds.
  • on push: Triggers when commits land on release branch.
  • branches: Limits trigger to release branch only.
  • permissions: Restricts workflow’s GitHub API access. contents: read, packages: write.
  • build-release job: Defines job for release binary creation.
  • runs-on self-hosted: Uses controlled runner with hardened environment and production toolchain.
  • checkout step: Retrieves code at specific commit.
  • Build release binary: Runs script that must be traceable and reproducible.
  • Upload artifact: Publishes binary to internal storage or package registry.

      - name: Get cloud token
        id: oidc
        uses: actions/github-script@v7
        with:
          script: |
            // OIDC token retrieval placeholder
      - name: Sign artifact
        run: ./sign-artifact.sh
      - name: Create attestation
        run: ./create-attestation.sh

Line-by-line explanation:

  • name: Names reusable workflow for secure artifact handling.
  • on workflow_call: Marks workflow as reusable. Other workflows can call it.
  • permissions id-token: write: Allows OIDC token issuance for cloud authentication.
  • permissions contents: read: Limits repository access to read-only.
  • sign-and-attest job: Defines job that signs artifacts and creates attestations.
  • runs-on ubuntu-latest: Uses hosted runner for signing and attestation tasks.
  • checkout step: Retrieves code and artifacts needed for signing.
  • Setup signer: Uses pinned third-party signer action at specific commit c0ffee123.
  • Get cloud token: Illustrative step using OIDC to obtain short-lived cloud token.
  • Sign artifact: Runs script to sign binary with controlled keys.
  • Create attestation: Runs script to generate artifact attestation metadata.

Debugging and governance method:

  • Reproduce: Identify exact workflow run, commit, and branch where an issue appeared.
  • Capture configuration: Record YAML definitions, branch protection settings, CODEOWNERS, and runner details at that time.
  • Isolate: Narrow down to specific job or step causing failure or risk. Disable non-essential steps temporarily.
  • Root cause versus escape point: Root cause is misconfiguration or defect in workflow, action, or script. Escape point is where branch protection, required checks, or attestations failed to catch it.
  • Governance: Update reusable workflows, branch rules, and action pinning policies. Document changes and tie them to safety and security cases.

Answer notes: A strong leader treats GitHub configuration as part of the EPS environment. They insist on clear branch rules, pinned actions, hardened runners, and artifact attestations. They use debugging and governance methods to turn incidents into structural improvements, not one-off fixes.
