Chapter 10: DevOps and release engineering

Source statusPractitioner knowledge. Not yet checked line by line against primary sources. Verify before quoting to a panel.
TakeawayA green pipeline is evidence. It is not approval. Vehicle readiness is a separate decision.

1. What DevOps means for an ECU Core

Continuous integration merges and tests changes often. Continuous delivery keeps every build releasable. Continuous deployment pushes to users automatically. Steering ECUs do not do the last one. Flashing a vehicle needs hardware validation, safety release decisions and customer approval. So the goal is a pipeline that produces a trustworthy release candidate on demand.

2. The release pipeline Level 2

Commit→Build→Static analysis→Unit tests→SIL→Security scan→HIL→Evidence pack→Sign and promote

BuildCross-compile with a pinned compiler and tool versionsEvery commit
Static analysisCoding-rule and defect checks (for example MISRA rules)Every commit
Unit tests, coverageFast logic checksEvery commit
SIL (software-in-the-loop)Run code against a simulated plantEvery merge
Security scan, SBOM, license checkFind vulnerable or disallowed dependenciesEvery merge
HIL (hardware-in-the-loop)Run on real ECU hardware with a simulated vehicleNightly, release candidates
Evidence packCollect results with the exact build identityRelease candidate

3. What makes it trustworthy Level 3

  • Reproducible build: same source and tools give the same binary. Without it, evidence cannot be tied to what ships.
  • Baseline: a frozen set of source, tools, configuration and calibration, with an identifier.
  • Immutable artifacts: a built binary is promoted, never rebuilt, between stages.
  • Provenance and signing: record who built what, and sign the result.
  • Quality gates: automatic checks block a merge or promotion. Manual approval is for decisions that need judgment, such as releasing with a deviation.

4. Why green is not ready Level 3

Failure caseAll checks pass. The vehicle shows a steering oscillation at low temperature. The simulated plant did not model friction at cold. Lesson: test environments have fidelity limits. Know what each stage cannot see, and keep vehicle validation in the plan.

Also check: flaky tests that were rerun until green, gates that were skipped, and results from a different build than the one shipping.

5. Metrics and maturity

Track build time, pipeline failure causes, flaky-test rate, time to repair a broken pipeline, release lead time and defects found after release. Adapt DORA's ideas, but do not count customer deployments, because there are none.

6. Questions a leader asks in a DevOps review

  • Can we rebuild the shipped binary bit for bit?
  • What does HIL not cover?
  • How long does a broken pipeline stay broken?
  • Who can bypass a gate, and is it logged?
What the interviewer testsWhether you know automation shortens evidence collection but does not replace release judgment.

7. Self-check and exercise

Exercise: Customer asks for a release in two days; HIL is red on one flaky test. Notes: do not rerun until green. Classify the failure, check the build identity, ask the test owner for root cause, and give the customer a date range with the evidence still needed.
