Chapter 08: Verification, Validation and ASPICE

Source statusDrafted with AI. Verify standards and product details against primary sources before relying on them.
TakeawayIf you cannot read the evidence chain, you cannot judge EPS release readiness, no matter how green the pipeline looks.

1. What you must know Core

Verification asks “did we build it right.” Validation asks “did we build the right thing.” Both must converge before release.

The V-model is a way of pairing development steps with test levels. Left side defines requirements and design. Right side defines tests that prove each level works.

Automotive SPICE (ASPICE) is a process assessment model for development and support activities. It rates how consistently teams follow defined practices [VERIFY]. It does not guarantee safety or quality by itself.

EPS torque-control sits in the middle of this. You must understand how requirements, models, code, and tests connect. Evidence must show coverage, fault handling, and realistic behavior, not just documents.

2. How it works Working

Traceability links requirements, design, implementation, and tests. Each safety-relevant requirement should trace to test cases and results. Each defect should trace back to the requirement or design it violated.

MIL, SIL, PIL, and HIL are test environments. MIL (Model-in-the-Loop) runs control models without code. SIL (Software-in-the-Loop) runs compiled software on a simulated platform. PIL (Processor-in-the-Loop) runs software on the target processor with simulated environment. HIL (Hardware-in-the-Loop) runs the full ECU against simulated vehicle dynamics.

Fault injection deliberately introduces faults to see how the system reacts. Coverage types measure how much of the design or code has been exercised. Examples include requirements coverage, branch coverage, and MC/DC coverage [VERIFY].

Requirements→Design→Implementation→MIL/SIL/PIL/HIL tests→Evidence and coverage→Release decision

Test effectiveness is how well tests detect defects that matter. Flaky tests are tests that sometimes pass, sometimes fail, without real changes. Fidelity limits are differences between test environments and real vehicles.

ASPICE evaluates whether these activities follow defined processes. It looks at planning, traceability, reviews, and test execution. It does not replace ISO 26262, which focuses on functional safety concepts [VERIFY]. Agile adds iterative development and continuous integration. You must align ASPICE, safety, and Agile without turning evidence into theater.

3. EPS example Working

Imagine an EPS program with a torque-control feature for lane-keeping assist. Requirements define assist levels, response times, and fallback behavior. Safety requirements define maximum unintended torque and fault reactions.

MIL tests run the control model against lane-change scenarios. They check that assist torque follows design curves and respects limits. SIL tests run the compiled torque-control software against the same scenarios, including sensor noise and communication delays.

PIL tests run the software on the target microcontroller. They measure worst-case execution time and CPU load during aggressive steering. HIL tests run the full ECU against a steering rig and vehicle dynamics model. They measure steering feel, fault reactions, and communication behavior.

Traceability links each requirement to MIL, SIL, PIL, and HIL tests. Fault injection introduces sensor failures, communication dropouts, and internal errors. Coverage metrics show how much of the torque-control logic and safety mechanisms have been exercised.

ASPICE assessments review whether requirements, design, implementation, and tests follow defined processes. They check traceability, reviews, and test management. ISO 26262 safety case collects evidence that safety goals are met. Agile practices drive frequent builds and tests.

4. How it fails (concrete scenario) Interview depth

Consider a program where the V-model exists only on slides. Requirements are vague. Traceability is partial. Tests focus on happy paths.

MIL and SIL tests show smooth torque curves. HIL tests show acceptable steering feel in standard maneuvers. Coverage metrics look high. ASPICE assessments rate processes as “managed” [VERIFY].

However, fault injection is weak. Rare sensor glitches and communication bursts are not tested. Flaky tests exist but are ignored. Fidelity limits are not discussed. Real vehicles experience rare steering jerks during combined maneuvers.

Another failure involves document theater. Teams produce traceability matrices and test reports to satisfy audits. Evidence is shallow. Tests do not reflect realistic driver behavior or worst-case timing. Release decisions rely on green dashboards, not deep analysis.

Agile practices can fail too. Frequent changes enter the codebase. Regression tests lag behind. Coverage drops silently. Safety case and ASPICE documentation are not updated. Release readiness becomes a guess.

5. What a manager decides (customer, safety, cybersecurity, schedule implications) Interview depth

You decide whether verification and validation are treated as checklists or as learning tools. You choose whether traceability is real or decorative. You decide whether MIL, SIL, PIL, and HIL are used strategically.

Customer implications are direct. OEMs ask for evidence, not slogans. They want to see how requirements map to tests. They ask how fault injection and coverage support steering safety. Weak answers damage trust.

Safety implications are severe. ISO 26262 safety goals depend on credible evidence. If tests miss critical scenarios, safety assumptions fail. ASPICE process ratings cannot compensate for missing coverage or weak fault injection.

Cybersecurity interacts with verification and validation. Security features add complexity and timing effects. Tests must cover security-related failure modes, such as invalid messages or blocked updates. Pipelines must protect test artifacts and configurations.

Schedule implications are unavoidable. Deep testing takes time. HIL rigs are scarce. Fault injection campaigns require planning. You decide whether to delay features or reduce test scope. You must explain these decisions to OEMs and internal stakeholders.

A green pipeline is evidence, not release approval. It shows tests passed under certain conditions. It does not prove that coverage is sufficient or that fidelity limits are understood. Release readiness requires a broader checklist and judgment.

6. Questions a strong manager asks the team Interview depth

Strong questions cut through document theater. They focus on evidence quality and limits.

  • Traceability: “Show me the chain from torque requirements to HIL tests and results.”
  • Test levels: “What do MIL, SIL, PIL, and HIL each add for EPS torque control?”
  • Fault injection: “Which faults did we inject, and how did the system respond?”
  • Coverage: “What coverage metrics do we track, and how do they relate to safety goals?”
  • Flaky tests: “Which tests are flaky, and what have we done about them?”
  • Fidelity limits: “Where do our test environments differ from real vehicles, and how do we compensate?”
  • ASPICE and safety: “How do ASPICE assessments and ISO 26262 safety case reinforce each other, not just coexist?”
  • Agile: “How do we keep traceability and coverage current under frequent changes?”

7. Weak answer versus strong answer Interview depth

Weak

“We follow the V-model and ASPICE. All tests are automated, and the pipeline is green. Coverage is above our target. ISO 26262 is handled by the safety team. Agile keeps us flexible.”

Strong

“Torque-control requirements trace to MIL, SIL, PIL, and HIL tests, including fault injection scenarios. We track requirements coverage and structural coverage for safety-relevant code. Flaky tests are either fixed or removed, with documented reasons. We document fidelity limits for each environment and use vehicle tests to close gaps. ASPICE assessments confirm process consistency, while the ISO 26262 safety case integrates test evidence. Agile changes trigger traceability updates and regression test selection.”

The weak answer hides behind frameworks and metrics. It ignores evidence quality and limits. It separates safety from development.

The strong answer shows integrated thinking. It connects test levels, coverage, and safety case. It treats ASPICE and Agile as tools, not shields.

8. What the interviewer is testing Working

Interviewers test whether you can read verification and validation evidence, not just approve plans. They want to see if you understand the V-model, traceability, and test levels at leadership depth.

They also test your ability to distinguish evidence from theater. Do you ask about fault injection, coverage, and fidelity limits? Do you challenge green dashboards? Do you connect ASPICE, ISO 26262, and Agile coherently?

They test your ability to lead release decisions. Do you talk about release-readiness checklists? Do you recognize that some risks remain? Do you show how you would explain decisions to OEMs and internal stakeholders?

9. Common mistakes (beginner and executive) Working

Beginners treat MIL, SIL, PIL, and HIL as buzzwords. They do not understand what each level reveals. They assume more levels automatically mean better testing.

Beginners also ignore flaky tests. They rerun until green and move on. They do not ask why tests are unstable. They accept coverage numbers without understanding what is covered.

Executives may treat ASPICE ratings as proof of quality. They focus on achieving a certain level. They do not ask whether processes produce meaningful evidence. They may push for ISO 26262 compliance without reading the safety case.

Executives sometimes confuse Agile speed with test depth. They celebrate frequent releases. They do not ask whether regression tests keep up. They may accept green pipelines as release approval.

Another mistake is ignoring fidelity limits. Leaders assume HIL equals reality. They do not ask how models differ from real vehicles. Surprises appear in fleet behavior.

11. Exercise with answer notes Expert

Scenario: An EPS program is approaching release. Dashboards show green pipelines, high coverage, and successful ASPICE assessments. However, recent vehicle tests reported rare steering jerks during combined maneuvers. The safety case is nearly complete.

Task: As lead software manager, build a release-readiness checklist and decide whether to release, delay, or conditionally approve. Each checklist item must have a one-line reason.

Release-readiness checklist with reasons:

  • Requirements traceability complete: Every safety-relevant torque requirement must link to tests and results, or gaps are visible.
  • MIL/SIL/PIL/HIL coverage of critical scenarios: Combined maneuvers and fault cases must appear across test levels, not just nominal runs.
  • Fault injection campaign reviewed: Injected faults must cover sensors, communication, internal errors, and reset behavior, with clear outcomes.
  • Coverage metrics interpreted, not just numbers: Requirements and structural coverage must be tied to safety goals, with known blind spots.
  • Flaky tests resolved or justified: Unstable tests must be fixed or removed, with documented risk assessment.
  • Fidelity limits documented: Differences between HIL, rigs, and vehicles must be understood, with compensating tests or margins.
  • Safety case aligned with evidence: ISO 26262 arguments must reference actual test results, not assumed behavior.
  • ASPICE findings integrated: Process weaknesses identified in assessments must be addressed or explicitly accepted with mitigation.
  • Agile change log reviewed: Late changes must have targeted regression tests and updated traceability.
  • Customer communication plan ready: OEMs must receive a clear explanation of residual risks and evidence.

Answer notes:

  • Assess evidence versus dashboards: Review traceability, test reports, and fault injection results. Do not rely solely on pipeline status or coverage percentages.
  • Investigate steering jerks: Treat vehicle reports as high-priority signals. Check whether reported maneuvers appear in MIL, SIL, PIL, and HIL tests. If not, design targeted tests.
  • Decide on release stance: If jerks are understood and mitigated, release with documented residual risk and monitoring. If root cause is unclear, delay release or limit deployment. Conditional approval might involve restricted use or additional fleet monitoring.
  • Integrate ASPICE and safety case: Use ASPICE findings to strengthen processes that support safety evidence. Ensure that safety case arguments reflect actual process maturity and test depth.
  • Align with Agile practices: Ensure that late changes are fully traced and tested. If Agile cadence outpaced verification, slow down or add stabilization iterations before release.
  • Communicate clearly: Explain decisions to OEMs and internal stakeholders using the checklist. Avoid vague assurances. Use concrete evidence and known limits.
