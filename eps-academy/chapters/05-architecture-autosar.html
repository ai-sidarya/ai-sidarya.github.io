Chapter 05: Architecture and AUTOSAR

Source statusDrafted with AI. Verify standards and product details against primary sources before relying on them.
TakeawayIf you cannot read the AUTOSAR layers, you cannot judge EPS torque-control safety, timing, or change impact.

1. What you must know Core

Architecture is how software pieces fit together, not just diagrams. AUTOSAR is a standardized architecture framework for automotive software. It defines layers, interfaces, and configuration concepts for ECUs.

Classic AUTOSAR targets microcontroller-based ECUs with static configuration. Adaptive AUTOSAR targets more dynamic, high-performance platforms [VERIFY]. EPS torque-control usually runs on Classic AUTOSAR today [VERIFY].

Key layers: application software, RTE (Runtime Environment), basic software, MCAL (Microcontroller Abstraction Layer), OS, communication and diagnostic stacks. You must understand how torque-control logic sits on top of these layers.

2. How it works Working

Application software contains software components (SWCs). Each SWC encapsulates related functionality. Runnables are the smallest executable units inside SWCs. The RTE connects SWCs to each other and to basic software.

Basic software includes communication stacks, diagnostic services, memory services, and OS integration. MCAL abstracts hardware registers and peripherals. The OS schedules tasks and runnables according to priorities and timing.

Communication stacks handle CAN, CAN FD, LIN, and Ethernet. Diagnostic stacks handle fault reporting and service requests. Calibration mechanisms allow changing parameters without recompiling.

Application SWCs→Runnables→RTE→Basic software→MCAL→Hardware

Layering separates concerns. Coupling is how strongly modules depend on each other. Cohesion is how well a module’s responsibilities fit together. Good architecture minimizes unnecessary coupling and maximizes cohesion.

LayerRoleEPS torque-control example
Application SWCsImplement domain logic.Torque calculation, plausibility checks, mode management.
RTEConnects SWCs and services.Delivers sensor data to torque SWC, sends commands to motor driver SWC.
Basic softwareProvides services.Communication, diagnostics, NVRAM, watchdog, OS integration.
MCALAbstracts hardware.ADC drivers for torque sensors, PWM drivers for motor control.
OSSchedules tasks.Runs torque-control runnable periodically, handles communication events.

Timing and memory budgets are allocated across layers. Each runnable has a period and worst-case execution time. Each SWC and stack consumes RAM and Flash. Variants and calibration add configuration complexity.

3. EPS example Working

Consider an EPS ECU using Classic AUTOSAR. The torque-control SWC receives torque and angle signals, plus vehicle speed. It outputs desired assist torque and mode information.

Runnables inside the torque SWC might include:

  • Torque_Read: Reads sensor data via RTE from ADC and communication SWCs.
  • Torque_Compute: Applies control algorithms and plausibility checks.
  • Torque_Output: Sends commands to motor driver SWC via RTE.

Communication SWCs handle CAN or Ethernet messages. Diagnostic SWCs handle fault codes and service requests. Calibration SWCs expose parameters such as assist curves and limits.

Basic software communication stacks implement CAN drivers, transport protocols, and network management. MCAL provides ADC and PWM drivers. The OS schedules runnables according to configured priorities and periods.

Variants appear when different vehicle platforms share the same ECU. One variant may use different assist curves, communication signals, or diagnostic behavior. Calibration allows tuning without changing code. Variant handling and calibration must respect timing and memory budgets.

4. How it fails (concrete scenario) Interview depth

Consider an architecture where torque-control runnables share a task with heavy diagnostics. The task period is tight. Diagnostics grow over time, adding more processing.

Under heavy diagnostic load, the task overruns its period. Torque_Compute runs late. PWM updates lag behind sensor changes. The driver feels steering lag or brief jerks.

Coupling can also cause failures. Torque SWC depends directly on communication SWC internals, not just RTE interfaces. A change in communication SWC breaks torque SWC behavior. A variant adds new signals, increasing complexity.

Technical debt accumulates when quick fixes bypass architecture. Extra flags, global variables, and ad-hoc calibration parameters appear. Cohesion drops. Understanding change impact becomes hard.

Adaptive AUTOSAR adds dynamic behavior. If EPS functions move to Adaptive platforms without careful timing analysis, real-time guarantees may weaken [VERIFY]. Scheduling and resource management differ. Torque-control may suffer.

5. What a manager decides Interview depth

You decide how architecture is challenged and maintained. You choose whether torque-control SWCs remain cohesive. You decide whether runnables share tasks with diagnostics or communication.

Customer implications are direct. OEMs expect clear architecture descriptions and predictable behavior. They ask how variants are handled and how calibration affects timing. You must answer with concrete architecture facts.

Safety implications involve timing and isolation. ASIL D torque-control goals require predictable execution and controlled dependencies. Architecture must support isolation of safety-critical functions from non-safety features.

Cybersecurity interacts with architecture. Communication and diagnostic stacks handle security features. Secure communication adds processing and latency. You must ensure security features do not break torque-control timing.

Schedule implications include architecture changes. Refactoring SWCs or tasks takes time. Variant handling and calibration changes require careful testing. You decide whether to accept architectural shortcuts or invest in cleanup.

You must challenge architecture without bypassing the architect. That means asking hard questions, not redesigning personally. You set constraints and priorities; the architect proposes solutions.

6. Questions a strong manager asks the team Interview depth

Strong questions focus on layering, timing, and change impact. They respect the architect’s role but demand clarity.

  • “Show me where the torque-control SWC sits in the AUTOSAR stack.”
  • “Which runnables implement torque calculation, and what are their periods and WCETs?”
  • “Which tasks host torque runnables, and what else runs there?”
  • “How do variants change SWC configuration, and how do we protect timing budgets?”
  • “How does calibration affect memory and execution time?”
  • “Which dependencies between SWCs are intentional, and which are technical debt?”
  • “How do communication and diagnostic stacks affect torque-control timing?”
  • “When we change a communication signal, how do we perform change-impact analysis?”

7. Weak answer versus strong answer Interview depth

Weak

“We use AUTOSAR, so the architecture is standard. The torque-control runs in an application component. Variants are handled by configuration. Timing is fine because the hardware is fast.”

Strong

“Torque-control is implemented in a dedicated SWC with three main runnables. They run in a high-priority task with defined periods and measured WCET. Diagnostics and communication run in separate tasks to protect timing. Variants change configuration but we track their impact on timing and memory budgets. Change-impact analysis covers SWC interfaces, RTE connections, and calibration parameters.”

The weak answer hides behind “standard” and “fast hardware.” It ignores timing, layering, and change impact. It does not show ownership.

The strong answer names SWCs, runnables, tasks, and budgets. It shows measurement and analysis. It treats AUTOSAR as a framework, not a guarantee.

8. What the interviewer is testing Working

Interviewers test whether you can read architecture diagrams and AUTOSAR concepts. They want to see if you understand SWCs, runnables, RTE, and basic software at leadership depth. They check whether you can connect architecture to torque-control behavior.

They also test your ability to challenge architecture constructively. Do you ask about timing budgets, memory usage, and coupling? Do you respect the architect’s role while insisting on clarity?

They test your understanding of variants and calibration. Do you recognize that configuration changes can break timing? Do you understand that technical debt hides in SWC dependencies?

9. Common mistakes (beginner and executive) Working

Beginners treat AUTOSAR as magic. They assume layering solves all problems. They ignore runnables and tasks. They focus only on SWC names.

Beginners also underestimate coupling. They allow SWCs to depend on each other’s internals. They bypass RTE interfaces. Technical debt grows quietly.

Executives assume architecture is “done” once diagrams exist. They push features and variants without revisiting timing and memory budgets. They treat AUTOSAR compliance as proof of safety.

Executives may bypass architects. They dictate solutions instead of constraints. Architects become implementers, not designers. Architecture drifts under pressure.

Another mistake is ignoring change-impact analysis. Leaders approve changes without asking which SWCs, runnables, and stacks are affected. Surprises appear in vehicle tests.

11. Exercise with answer notes Expert

Architecture review case: You join an EPS program using Classic AUTOSAR. Field tests show occasional steering lag during rapid lane changes. The architect presents a diagram showing torque-control SWC, diagnostics SWC, communication SWC, and tasks.

Task: Conduct a leadership-level architecture review. Focus on timing, layering, variants, and technical debt. Outline questions and possible actions.

Answer notes:

  • Timing and tasks: Ask which tasks host torque runnables and what else runs there. Request measured WCET and CPU load for torque tasks under worst communication and diagnostic load. If diagnostics share the same task, discuss separating them or adjusting priorities.
  • Layering and dependencies: Ask how torque SWC interacts with communication and diagnostics. Check whether it uses only RTE interfaces or accesses internals. Identify any global variables or cross-layer shortcuts. Propose refactoring to reduce coupling and improve cohesion.
  • Variants and calibration: Ask how variants change SWC configuration and calibration. Request timing and memory budgets per variant. If variants add features without revisiting budgets, insist on updated analysis. Consider limiting variant complexity or splitting SWCs.
  • Technical debt: Ask for examples of past quick fixes. Identify flags, ad-hoc parameters, or duplicated logic. Discuss a plan to pay down technical debt, starting with safety-critical paths. Tie this plan to milestones and customer communication.
  • Change-impact analysis: Ask how changes to communication signals or diagnostics are analyzed. Request a documented process linking SWCs, runnables, tasks, and stacks. If the process is weak, propose strengthening it and making it part of release criteria.
  • Leadership stance: Clarify that you set constraints: predictable timing, controlled coupling, and clear variant handling. Invite the architect to propose solutions within those constraints. Commit to supporting architecture changes in planning and customer discussions.

This exercise shows whether you can lead architecture discussions without drawing boxes yourself. It reveals your ability to connect AUTOSAR concepts to steering behavior, safety goals, and program decisions.
